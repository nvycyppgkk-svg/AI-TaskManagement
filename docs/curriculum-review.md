## 第1章 インターネットとネットワークの仕組み

### Q1. インターネットとは

**Q.** 「インターネット」と「Webブラウザで見るホームページ」は同じものですか？違うとすれば、どう違いますか？

**A.**
インターネットは、世界中の無数のネットワーク（家庭・企業・大学など）が標準的なプロトコル（TCP/IP）で相互接続された「ネットワーク自体」を表す。

一方、Webブラウザで見るホームページは、そのインターネット上で動く「サービスのひとつ」であり、HTTP/HTTPS というプロトコルを使ってWebサーバから情報を取得して表示する仕組み（= World Wide Web）に当たる。

インターネット上で動くサービスはWebだけでなく、メール・FTP・DNSなども含まれる。インターネットがインフラ（道路網）で、Webブラウザで見るホームページはそのインフラ上で動くサービス（車）のひとつ、という関係。

### Q2. IPアドレスとポート番号

**Q.** `localhost` とは何を指しますか？ `:5173` や `:8080` のようなポート番号はなぜ必要ですか？

**A.**
`localhost` は自分自身のコンピュータのホスト名を表す。IPアドレスで表すと `127.0.0.1` に対応しており、外部ネットワークに出ず自分のPC内で完結する通信を指す。開発時に外部に公開せずローカルで動作確認できるのはこのため。

ポート番号は、ホスト上で複数のサービスやプロトコルが同時に動いている際に、それらを識別するために必要。

例えとしては「マンションの部屋番号」が分かりやすい。`localhost`（IPアドレス）がマンションの住所、ポート番号が部屋番号。同じ建物（PC）に届いた通信を、どの部屋（サービス）に渡すかを番号で振り分けている。

このプロジェクトでは、同じ `localhost` に対して `:5173`（Vite/フロントエンド）と `:8080`（Spring Boot/バックエンド）という別々の部屋番号で2つのサービスが同時に動いている。

### Q3. DNS

**Q.** ブラウザのアドレスバーに `https://www.example.com` と入力してからページが表示されるまでに、DNSはどのような役割を果たしますか？

**A.**
DNS（Domain Name System）は、ドメイン名に紐づくIPアドレスを特定するために存在する。

人間は `www.example.com` という名前で覚えているが、コンピュータは `93.184.216.34` のようなIPアドレスでしか通信できない。DNSはその名前引きをしてくれる仕組みで、「電話帳」のような役割を果たす。

流れとしては以下の通り：

1. ブラウザが `www.example.com` のIPアドレスをDNSサーバに問い合わせる
2. DNSサーバがIPアドレスを返す
3. ブラウザはそのIPアドレスのサーバにHTTPリクエストを送る
4. サーバがHTMLを返してページが表示される

### Q4. HTTPとは

**Q.** HTTPとは何の略で、どのような役割を持つものですか？「プロトコル」という言葉の意味も含めて説明してください。

**A.**
プロトコルとは、通信をするための「約束事・ルール」のこと。日本語で話しかけて日本語で返す、という共通ルールがないと会話が成立しないように、クライアントとサーバが共通のルールで話すことで初めてデータのやり取りができる。HTTPもそうしたプロトコルの一つ。

HTTPは「HyperText Transfer Protocol」の略で、インターネット上のWebサイトにアクセスする際にHTML、CSS、画像などの情報を取得するために使われる。HTMLやCSSだけでなく、このアプリのようにJSONデータ（API通信）もHTTPで運ばれており、「Web上のあらゆるデータを運ぶ共通の手段」と言える。

### Q5. HTTPとHTTPSの違い

**Q.** HTTPとHTTPSの違いは何ですか？ なぜ現在のWebサイトはほぼすべてHTTPSを使用していますか？

**A.**
HTTPは暗号化がされていない通信で、HTTPSは暗号化が常にされた状態で行われる通信。HTTPSの「S」は「Secure」の略で、TLS（Transport Layer Security）という仕組みで通信を暗号化している。

HTTPで通信すると、途中の第三者に通信内容を盗み見られたり（盗聴）、改ざんされたりするリスクがある。パスワードやクレジットカード番号が平文で流れてしまうことになり、セキュリティ上のリスクが大きい。

現在HTTPSが普及している理由はセキュリティだけでなく、GoogleがHTTPS対応サイトをSEOで優遇していること、ブラウザが「保護されていない通信」と警告を出すことなども大きな要因。

### Q6. リクエストとレスポンス

**Q.** Webにおける「リクエスト」と「レスポンス」の関係を、日常生活の例えを使って説明してください。

**A.**
飲食店でメニューを注文することを「リクエスト」、店員が注文した料理を届けることを「レスポンス」に例えられる。

- 客（クライアント/ブラウザ）が注文（リクエスト）を出す
- 店員（サーバー）が厨房（データベースなど）から料理を用意して届ける（レスポンス）
- 注文内容が間違っていれば「それはできません」と返事が返る（エラーレスポンス＝400番台）
- 厨房が火事になっていたら「今日は提供できません」と返事が返る（サーバーエラー＝500番台）

重要なポイントとして、**Webの通信は必ず「リクエストが先、レスポンスが後」で、サーバーから勝手にレスポンスが来ることはない**という性質がある（客が注文しない限り、料理は運ばれてこない）。

### Q7. HTTPメソッド

**Q.** GET / POST / PUT / DELETE / PATCH とは何ですか？日常生活の例えで、それぞれの違いを説明してください。

**A.**
HTTPメソッドは、クライアントがサーバに「何をしてほしいか」を伝える決まり事。同じURLでも、メソッドが違えば処理内容が変わる。

手紙に例えると：

| メソッド | 役割 | 手紙の例え |
|---|---|---|
| GET | データの取得 | 手紙を受け取る（送り手の状態は変わらない） |
| POST | データの新規作成 | 新しい手紙を投函する（新規に手紙が作られる） |
| PUT | データの全体更新 | 手紙を丸ごと新しいものに書き換える |
| PATCH | データの部分更新 | 手紙の表紙だけを張り替える（中身はそのまま） |
| DELETE | データの削除 | 手紙を捨てる |

**PUTとPATCHの違いのポイント**
PUTは「リソース全体を置き換える」、PATCHは「一部のフィールドだけを更新する」。例えば名前だけ変えたい場合、PUTだと他のフィールドも全部送らないといけないが、PATCHなら変更したいフィールドだけ送ればよい。

**このアプリでの実例**
- `GET /api/boards` → ボード一覧取得
- `POST /api/boards` → 新規ボード作成
- `PATCH /api/boards/{id}` → ボード名だけ変更
- `DELETE /api/boards/{id}` → ボード削除

### Q8. HTTPステータスコード

**Q.** 200 / 201 / 400 / 404 / 500 はそれぞれ何を意味しますか？

**A.**

| コード | 意味 | 内容 |
|---|---|---|
| 200 | OK | リクエスト成功 |
| 201 | Created | リソースが作成された |
| 400 | Bad Request | リクエストの形式が不正 |
| 404 | Not Found | リソースが存在しない |
| 500 | Internal Server Error | サーバー内部のエラー（例外の発生など） |

ステータスコードは3桁の最初の数字で大まかな分類ができる：

| 分類 | 意味 |
|---|---|
| 1xx | 情報（処理中） |
| 2xx | 成功 |
| 3xx | リダイレクト |
| 4xx | クライアント側のエラー |
| 5xx | サーバー側のエラー |

「4xxは自分（クライアント）が悪い」「5xxはサーバーが悪い」と覚えると区別しやすい。

**このアプリで実際に使われているコード例**
- `GET /api/boards` 成功 → 200 OK
- `POST /api/boards` でボード作成成功 → 201 Created
- `DELETE /api/boards/{id}` 削除成功 → 204 No Content
- 存在しないボードIDを指定 → 404 Not Found
- ボード名が空で作成試行 → 400 Bad Request

### Q9. JSONとは

**Q.** JSONとは何ですか？ なぜ広く使われていますか？

**A.**
JSON（JavaScript Object Notation）は、データを人間にも機械にも読みやすい形で表現するためのテキスト形式。元々JavaScript由来の記法だが、現在は言語を問わず標準的なデータ交換形式になっている。

具体例（このアプリのAPIレスポンス）：

```json
{
  "id": 1,
  "name": "プロジェクトA",
  "lists": [
    { "id": 1, "name": "To Do" },
    { "id": 2, "name": "進行中" }
  ]
}
```

広く使われる理由：

1. **人間が読み書きしやすい**（デバッグや目視確認が容易）
2. **軽量**（XMLなど他の形式よりデータ量が少ない）
3. **言語非依存**（JavaScript、Java、Pythonなど、どの言語にもパーサーがある）
4. **構造化データを表現できる**（オブジェクト・配列・ネストが自然に書ける）

このアプリでは、フロントエンド（TypeScript）からバックエンド（Java）へ、オブジェクトをJSON文字列に変換（シリアライズ）して送信。バックエンドはJSON文字列をJavaのオブジェクト（例: `BoardCreateRequest` クラス）に変換（デシリアライズ）して処理する。この変換はSpring Bootが自動で行う（`@RequestBody` アノテーションの役割）。

### Q10. APIとは

**Q.** APIとは何ですか？ なぜ直接データベースにアクセスしないのですか？

**A.**
API（Application Programming Interface）は、あるプログラムやアプリの機能を外部のプログラムが使用できるようにする仕組み・ルール。「ソフトウェア同士がやり取りするための窓口・契約」のイメージ。

身近な例えとして「レストランのメニュー」が分かりやすい。客（フロントエンド）は厨房（データベース）に直接入らず、メニュー（API）から注文する。店員（API）が注文を受けて厨房に伝え、料理を運んでくる。

**なぜ直接DBにアクセスしないか：**

1. **セキュリティ**
   - DBに直接アクセスできる＝DBの認証情報をフロントエンドに持たせることになる。フロントのコードはブラウザで誰でも読めるので、情報が漏れたら誰でもDBを直接操作できてしまう
   - APIを挟むことで「このユーザーは本当にこの操作をしていいのか」を認証・認可でチェックできる

2. **ビジネスロジックの集約**
   - 「ボードを作成する時は、同時にデフォルトリスト3つを作成する」といったルールを、APIサーバー側で一箇所にまとめられる
   - フロントとDBを直接繋ぐと、こうしたルールを各画面で書く必要があり、バグや漏れが発生する

3. **DBの変更に強くなる（疎結合）**
   - DBのテーブル構造を変えても、APIの形（レスポンス形式）が同じなら、フロントは何も変えなくていい
   - 逆もしかりで、フロントの技術をReactからVueに変えてもAPIは同じものを使える

4. **アクセス元の多様性**
   - Webブラウザだけでなく、スマホアプリ、他のサーバーからも同じデータを使いたい場合、APIが共通窓口になる

### Q11. CORSとは

**Q.** CORSとは何のためにありますか？

**A.**
CORS（Cross-Origin Resource Sharing）は、プロトコル・ドメイン・ポートの組み合わせで決まる「オリジン」間の通信について、サーバ側がどのオリジンを許可するかを制御する仕組み。

背景には **同一オリジンポリシー（Same-Origin Policy）** というブラウザのセキュリティ機構がある。ブラウザは本来、「現在見ているページと同じオリジンにしかリクエストを送れない」という制限をかけている。これは悪意のあるサイトが、ユーザーのログイン済みの別サイト（銀行サイトなど）に勝手にリクエストを送るのを防ぐため。

CORSは「サーバー側が特定のオリジンだけ例外的に許可する」仕組み。

**このアプリでの実例：**
- フロント `localhost:5173` → バック `localhost:8080` はポートが違うので「別オリジン」扱い
- `CorsConfig.java` で `allowedOrigins("http://localhost:5173")` と明示的に許可している
- 以前、`DELETE` メソッドを `allowedMethods` に追加し忘れていたため、ボード削除が失敗したのもCORSの制御によるもの

**流れのイメージ：**
1. ブラウザが別オリジンへリクエストを送る前に、サーバーに「このオリジンからアクセスしていい？」と事前確認（プリフライトリクエスト＝OPTIONSメソッド）を送る
2. サーバーが許可レスポンスを返す
3. ブラウザが実際のリクエストを送る

### Q12. クライアントとサーバー

**Q.** 「クライアント」と「サーバー」とは何ですか？ このアプリの構成の中で、それぞれどれがクライアントでどれがサーバーですか？

**A.**
ある特定のアプリケーションやプログラムを提供する機能を持つのが**サーバ**、そのアプリやプログラムを外部から閲覧したり利用する側が**クライアント**。

- サーバーとは「要求を受けて、応答を返すプログラム」
- クライアントとは「要求を出して、応答を受け取るプログラム」

このアプリでは：

| 関係 | クライアント | サーバー |
|---|---|---|
| ユーザー → アプリ | ブラウザ | バックエンド |
| アプリ → DB | バックエンド | データベース |

つまり**バックエンドは、ブラウザから見ればサーバーだが、DBから見ればクライアント**という二重の役割を持っている。クライアント・サーバーは固定的な役割ではなく、相対的な関係である。

**このアプリでの流れ：**
```
[ブラウザ] ──リクエスト──> [バックエンド] ──SQL──> [データベース]
   クライアント           サーバー兼クライアント       サーバー

[ブラウザ] <──レスポンス── [バックエンド] <──結果── [データベース]
```
